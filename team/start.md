# рабочее подключение команды: gconf-core и telegram

рабочий проект всей команды — `https://github.com/matskevich/gconf-core`. установочный пакет telegram mcp — инфраструктура этого проекта. готовность означает доступ к проекту, подписку на канал владельца и проверенную работу через mcp.

## действия локального codex

1. проверь текущий github-аккаунт через `gh api user --jq .login`, затем доступ к `matskevich/gconf-core`. найди существующий clone по точному origin; при отсутствии клонируй в отдельную локальную папку. не используй старые `matsako/gconf*`. при отказе доступа верни github-login, точную ошибку и останови только проектную часть; владелец выдаст доступ. токены не запрашивай и не выводи.
2. открой рабочий чат codex в найденном gconf-core. прочитай `AGENTS.md`, `CONTEXT.md` и `docs/repo-map.md`. telegram-инфраструктура и сессии хранятся вне репозитория.
3. пройди персональную установочную инструкцию. источник — только `matskevich/tg-mcp-guarded`, канал — `https://raw.githubusercontent.com/matskevich/tg-mcp-guarded/main/team/stable.json`. сверь файлы runtime с хешами канала. действующие credentials и сессии владельца не копируй.
4. после prepare выполни из gconf-core найденным python 3.11+:

```sh
python3 scripts/telegram-team-onboarding/subscription.py subscribe --operator YOUR_OPERATOR --project /absolute/path/to/gconf-core
```

`YOUR_OPERATOR` — `anna`, `karina` или `natasha` из персонального сообщения. подписка проверяет официальный канал ежедневно через launchagent и сохраняет статус локально. это проверка обновлений; новая версия применяется агентом с последующей проверкой аккаунта и guards, а не заменяется незаметно во время работы.

5. создай или дополни локальный `~/.codex/skills/gconf-telegram/SKILL.md` без перезаписи чужого содержимого: все telegram-задачи gconf выполнять из этого проекта через `gconf-<operator>-read/actions`; перед началом читать эту инструкцию и запускать `subscription.py check`. при несовпадении версии сначала подготовить обновление из канала; не делать рассылки на устаревшем или непроверенном runtime. локальную установку менять с сохранением `.env`, `data/`, сессий, конфигурации и старого кода для отката. затем проверить imports, guards, account identity и read-back. если выпуск требует новой схемы/зависимостей без инструкции миграции — остановить обновление и сообщить блокер.
6. после авторизации открой новый чат именно в gconf-core. вызови `tg_auth_status` у read/actions, прочитай собственный чат, отправь тест в него через штатный action mcp (allowlist, dry_run → approval code → minimum age → confirm с точным confirmation_text, process guard) и прочитай результат через read. остальные telegram-интеграции не использовать для задач этого аккаунта. конфигурация без фактического вызова инструментов не доказывает готовность.
7. общие инструкции и обезличенные результаты работы сохраняй в gconf-core, синхронизируй через git: перед задачей fetch; обновление чистой ветки только fast-forward; собственные изменения отдельным коммитом и push/обычным review-процессом. при чужих изменениях или конфликте сохраняй работу и сообщай состояние, не reset/stash вслепую. raw чаты, контакты, сессии, credentials и персональные квитанции остаются в приватном operational storage.

## квитанция готовности

верни одним компактным сообщением: github-login; origin и commit gconf-core; версия канала и совпадение runtime; subscription_registered/daily_check_loaded; имена обоих mcp; account identity; id тестовой отправки и read-back; локальный skill установлен; блокер. секреты и содержимое клиентских чатов не включать. отправка квитанции человеку остаётся под его контролем.

если есть только скачанный пакет или установленная конфигурация, статус — подготовлено. принятие требует всех проверок выше. доступ к проекту, desktop и mcp фиксируются отдельно.
