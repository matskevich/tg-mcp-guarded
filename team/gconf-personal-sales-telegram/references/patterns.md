# паттерны персональных продаж

## чтение и аналитика

- начни с доступных инструментов текущего read mcp, а не предположений о старой версии api. основные возможности: `tg_auth_status`, `tg_get_messages`, `tg_get_messages_since`, `tg_get_group_info`, `tg_resolve_username`, `tg_get_my_dialogs`, `tg_download_media`.
- при продолжении читай только новые сообщения после watermark. при неполной выдаче проверь границы и pagination; отсутствие в текстовой проекции не доказывает отсутствие вложения или реакции.
- до пересказа voice/video используй доступную штатную транскрипцию. если её нет, пометь материал как необработанный, не выдумывай содержание.
- для каждого вывода сохраняй private provenance: диалог, id сообщения, время, границы чтения. в общий проект переноси только обезличенные выводы и механики продаж.
- разделяй наблюдение и интерпретацию. не считай предложение принятым, документ прочитанным или оплату совершённой по одному исходящему сообщению.

## действия, если они поручены

- только actions mcp, правильный аккаунт, точный целевой диалог и allowlist. штатный поток: `dry_run=true` → `approval_code` → выдержать `approval_min_age_sec` → тот же payload с `confirm=true` и точным `confirmation_text` → read-back через read mcp.
- фраза подтверждения — внутренний контроль инструмента; прямое разрешение человека на конкретную отправку не превращай во второй разговорный запрос разрешения.
- `TG_ENFORCE_ACTION_PROCESS=1` сохраняется. прямые telethon writes и обход idempotency не использовать. при зависании после отправки сначала проверь точный текст в диалоге, потом решай о повторе.
- если нативные actions не видны, используй `scripts/tg_action_bridge.py` существующего официального runtime. это клиент того же action mcp, а не замена процесса.
- тестовый allowlist не расширяет полномочия на клиентов. для порученной клиентской отправки настрой точный разрешённый target, сохранив остальные ограничения. само чтение не является поручением отправки.

## общий проект

изменения общих playbooks и обезличенные результаты — gconf-core с обычной git-синхронизацией. перед задачей fetch; обновление чистой ветки через fast-forward. чужие и свои незакоммиченные изменения сохраняй. raw pii, пароли, сессии и runtime receipts остаются в приватном operational storage.

официальные расширенные материалы находятся в `docs/` и `README.md` исходного tg-mcp-guarded. выбирай только раздел, нужный для текущей задачи. устаревший пример из документации не отменяет текущие tool schema и policy.
