# tg-mcp: рабочие примеры

это сценарии для адаптации под конкретную задачу. placeholders обозначены угловыми скобками; не вызывайте инструменты с ними буквально. сначала проверьте аккаунт через `tg_auth_status`. точные имена инструментов и поля сверяйте с подключённым сервером.

## найти человека и поднять нужный фрагмент

запрос владельца: «найди, что мы отправляли этому человеку про установку».

1. `tg_search_contacts(query="<имя или username>", limit=5)`; для известного handle — `tg_resolve_username(username="<handle>")`.
2. проверьте id и username получателя; при необходимости прочитайте `tg_get_group_info(group="<peer>")`. совпадение имени недостаточно. для существующей переписки допустим ограниченный `tg_get_my_dialogs(limit=50, dialog_type="user")`.
3. `tg_search_messages(group="<peer>", query="установка", limit=20, date_from="2026-09-01", date_to="2026-10-18")`. даты здесь — пример; используйте период задачи.
4. поднимите ближайший контекст нужного попадания: `tg_get_messages(group="<peer>", limit=10, offset_id=<message_id + 1>)`.
5. верните факты с peer id, message id и датой; остановитесь, когда найден нужный материал. следующий поиск нужен только для оставшегося конкретного пробела.

для периода используйте `tg_get_messages_since(group="<peer>", cutoff_iso="<начало периода>", limit=50)`: явный лимит обязателен для ограниченной задачи, так как default `limit=0` допускает большой объём. если лимит достигнут, пометьте покрытие как неполное и продолжайте пагинацию только когда это нужно запросу.

numeric peer из подтверждённого ответа устойчивее имени. если отдельный инструмент не разрешает numeric id, попробуйте известный username, сначала сверив, что он разрешается в тот же id. пустая выдача без проверки peer не доказывает отсутствия переписки.

## отправить конкретный текст и получить receipt

запрос владельца: «отправь этому человеку согласованный текст». это полномочие на точные target и payload; при неоднозначности сначала уточните недостающий объект.

1. проверьте actions identity и `tg_get_actions_policy`: разрешённый target, лимиты, обязательные защиты. backend не читает мысли владельца и не устанавливает полномочия агента.
2. прочитайте `tg_get_messages(group="<peer>", limit=5)` и сохраните максимальный id как watermark. сохраните финальный payload без дальнейшего редактирования.
3. `tg_send_message(group="<allowlisted peer>", message_text="<точный текст>", dry_run=true)`.
4. проверьте preview, сохраните `approval_code`, `action_hash`, `approval_execute_after_ts` и `confirmation_text_required`. дождитесь указанного времени до выполнения.
5. тот же запрос с `dry_run=false, confirm=true, confirmation_text="<точная настроенная фраза>", approval_code="<код из preview>"`.
6. `tg_get_messages(group="<peer>", limit=20, min_id=<watermark>)`. найдите новое сообщение с байт-точным текстом, ожидаемым sender id и временем отправки. если пришло 20 сообщений и нужное ещё не найдено, проверьте покрытие диапазона.
7. сохраните `target_id`, `account_id`, исходный watermark, новый `message_id`, `action_hash` и результат точного сравнения.

`tg_send_message` в этой версии возвращает `success` без нового message id. `success=true` подтверждает результат вызова; `delivery_verified` требует независимого read-back. при таймауте, `outcome_unknown`, недоступном sender id или нескольких неразличимых совпадениях сохраните неопределённость и проверьте фактическую историю. не дублируйте отправку автоматически. `force_resend=true` нужен только для намеренного повтора внутри текущих полномочий.

когда native actions не виден, разрешён fallback `scripts/tg_action_bridge.py`: он обращается к тому же action mcp. сначала проверьте `tools`, auth и policy. `write-call` делает dry-run, ждёт заданный интервал и выполняет действие; запускайте его только после проверки точной области полномочий. в этой версии `auto` берёт задержку из окружения bridge, а не из preview: wrapper может скрыть свои env. передавайте проверенные по policy `--approval-wait-sec` и `--confirmation-text` явно либо используйте отдельные `call` для dry-run и confirm после `approval_execute_after_ts`. проверяйте `preview.success` и `execution.success`: exit code bridge сам по себе не доказывает успешную отправку. конфигурация по умолчанию — codex `~/.codex/config.toml`; другой клиент не получает поддержку автоматически. если подходящей конфигурации нет, используйте свой mcp-клиент, сохранив те же проверки. прямой telethon write запрещён.

## написать как ассистент

черновик, без отправки:

```text
это ассистент алексея.

нашёл инструкцию по подключению и три примера для первого запуска: <ссылка>.
начни с проверки своего аккаунта и чтения одного чата. если упрёшься в конкретный шаг, пришли текст ошибки без секретов — проверю его.

— ассистент алексея
```

имя, подпись, язык и регистр — настройки владельца, этот пример их не устанавливает. ассистент говорит о собственной работе и различает слова владельца, факты и свою интерпретацию. не превращает draft в обещание и отправленное сообщение в ответ человека. для ручного копирования в telegram весь текст отдаётся одним plain-text блоком с буквальными номерами и ссылками; api parse mode нельзя предполагать.

## понять голосовое или скачать документ

запрос владельца: «возьми голосовое из этого сообщения и сделай конспект».

1. проверьте источник через `tg_get_messages`: сохраните peer id, message id, дату, `has_media`, mime/name/size. пустой text при наличии медиа не означает отсутствия содержания; mime сам по себе не доказывает, что это voice note.
2. `tg_download_media(group="<peer>", message_id=<id>, output_dir="<приватная папка>")`; проверьте существование возвращённого файла, тип и ненулевой размер.
3. используйте уже установленный в этой среде локальный распознаватель. если у владельца есть `stt-transcribe`, пример: `stt-transcribe <media-file> --lang ru`. это внешняя зависимость, репозиторий её не устанавливает.
4. сохраните transcript рядом с приватным source receipt; конспект привяжите к message id и таймкодам, если они получены. имена и неясные слова пометьте как неопределённые.
5. верните `transcribed`, `cached` или `media_unprocessed` с путём/причиной. при `media_unprocessed` уточните стадию: ещё не скачано, недоступно или скачано без распознавания. не называйте такой материал прослушанным.

нет stt — сообщите одну недостающую зависимость и продолжите доступную текстовую часть. не запускайте параллельные расшифровки одного файла, не скачивайте модель и не загружайте запись во внешнее облако без отдельного решения. готовый transcript из чата можно использовать с пометкой его происхождения.

для pdf/фото первые два шага те же; дальше нужен соответствующий локальный reader. dm download использует exact id и fallback до 500 последних сообщений того же peer. ошибка скачивания старого сообщения не доказывает потери файла; [детали](DM_MEDIA_DOWNLOAD_FALLBACK.md).

## выбрать кнопку в боте

прочитайте актуальный `buttons` через `tg_get_messages`; проверьте `is_callback`, текст, `row`/`col` и message id. `tg_click_inline_button` выполняет inline callback с обычными dry-run/approval/confirm gates. после вызова прочитайте новый экран бота: timeout callback может сопровождаться уже выполненным действием.

url, web-app и reply-keyboard не являются поддерживаемыми callback-кнопками. для явно заданной последовательности в одном разрешённом диалоге есть `tg_run_bot_steps`: `send_message`, `click_button`, `wait`. после частичного результата сначала установите, на каком шаге находится бот; всю цепочку не повторяйте автоматически. покупка или выдача доступа требуют соответствующих полномочий независимо от формы кнопки.
